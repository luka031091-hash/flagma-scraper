# Flagma Scraper — Apify-актор для збору оголошень Flagma.ua

**Дата:** 2026-06-11
**Статус:** чернетка на погодження
**Назва актора:** `flagma-scraper`

## 1. Призначення і межі

Самостійний Apify-актор, що скрейпить оголошення з Flagma.ua за заданими URL і
складає структурований датасет. **Лише збір даних** — без арбітражної логіки.

Зіставлення «куплю ↔ продам» і розрахунок маржі — **окремий інструмент пізніше**.
Цей актор готує сирий, чистий датасет, на якому той інструмент працюватиме.

**Що актор НЕ робить:** не зіставляє позиції, не рахує маржу, не авторизується,
не обходить капчу, не скрейпить інші платформи (OLX/Prom), не працює за розкладом
(запуск ручний; Apify Schedule — пізніше за бажанням).

## 2. Контекст

Цей актор — самостійний інструмент збору даних. Орієнтир — товарний арбітраж на
українських майданчиках, для якого цей датасет є сировиною; зіставлення позицій і
розрахунок маржі лишаються за окремим інструментом.

Готового актора для Flagma.ua в Apify Store немає (перевірено через `apify actors
search` і Store API) — тому будуємо власний.

## 3. Стек і архітектура

- **Crawlee `CheerioCrawler`** (HTTP, без браузера) + Apify SDK, Node.js.
- Шаблон старту: `apify create flagma-scraper --template js-crawlee-cheerio`.
- **Двофазний краул через роутер** (мітки запитів):
  - `LIST` — сторінка пошуку/категорії: парсить картки → ставить у чергу `DETAIL`
    для кожного лоту + наступну сторінку пагінації як `LIST`.
  - `DETAIL` — сторінка оголошення: парсить усі поля + виконує **reveal телефону**
    окремим HTTP-запитом → пише запис у dataset.

### 3.1 Модулі

| Файл | Відповідальність |
|---|---|
| `main.js` | Вхід: читає Input, конфігурує краулер, запускає |
| `routes.js` | Хендлери `LIST` і `DETAIL` |
| `phone.js` | Інкапсулює логіку reveal телефону (єдине місце знань про endpoint — легко правити) |
| `selectors.js` | Усі CSS-селектори в одному місці (стійкість до зміни розмітки) |
| `normalize.js` | Розбір ціни/валюти/одиниці, очистка тексту, виділення `id` |

## 4. Потік даних

```
startUrls (LIST) ──┬─► наступна сторінка (LIST) ──┐
                   │                               │ (пагінація, поки є наступна)
                   └─► кожне оголошення (DETAIL) ──┘
                              │
                   парс полів + reveal телефону (HTTP)
                              │
                          Apify Dataset ─► CSV / JSON / Excel
```

`sourceStartUrl` передається з `LIST` у `DETAIL` через `request.userData`, щоб у
кожному записі було видно, з якої стартової сторінки він прийшов.

## 5. Вхідні параметри (INPUT_SCHEMA)

| Параметр | Тип | Дефолт | Призначення |
|---|---|---|---|
| `startUrls` | array (обовʼязково) | — | URL сторінок пошуку/категорій Flagma |
| `maxItems` | integer | 0 (без ліміту) | Ліміт лотів за запуск |
| `maxRequestsPerMinute` | integer | 60 | Обмеження темпу (анти-бан) |
| `maxConcurrency` | integer | 5 | Помірний паралелізм (анти-бан) |
| `fetchPhones` | boolean | true | Чи виконувати reveal телефону |
| `proxyConfiguration` | object | Apify Proxy увімкнено | Проксі |

**Rate limiting — свідомо спрощено:** один механізм `maxRequestsPerMinute` +
помірний `maxConcurrency`. Окремий `minDelayMs` НЕ додаємо — це дублювало б
нативний механізм Crawlee.

## 6. Структура запису в датасеті

```jsonc
{
  "id": "123456",                 // унікальний id оголошення (див. §7)
  "url": "https://flagma.ua/...",
  "sourceStartUrl": "https://flagma.ua/products/...",  // звідки прийшов лот
  "listingType": "продам",        // "продам" | "куплю" | null (евристика)
  "title": "...",
  "description": "...",
  "rawPrice": "2 800 $/шт",        // оригінальний текст ціни (вкл. "договірна")
  "normalizedPrice": 2800,         // число або null
  "currency": "USD",               // "UAH" | "USD" | "EUR" | null
  "priceUnit": "шт",               // "шт" | "кг" | "т" | ... | null
  "category": "...",
  "seller": { "name": "ТОВ ...", "type": "ТОВ" },  // type: ФОП | ТОВ | приватна | null
  "location": { "city": "...", "region": "...", "country": "UA" },
  "phone": "+380...",              // з reveal; null якщо не отримано
  "phoneStatus": "found",          // found | hidden | failed | disabled (див. §8)
  "images": ["https://..."],
  "publishedAt": "...",            // дата публікації або null
  "scrapedAt": "2026-06-11T..."    // ISO timestamp збору
}
```

Output schema згенеруємо skill-ом `apify-generate-output-schema` — поля будуть
типізовані й гарно показані в UI Apify.

### Ціна — `rawPrice` + `normalizedPrice`

Flagma має ціни в різних форматах («200 грн/шт», «2 800 $/шт», «договірна»,
«за домовленістю»). `rawPrice` зберігає оригінальний рядок (зокрема нечислові
значення), `normalizedPrice` — виділене число (або `null`, якщо ціна нечислова).
Це запобігає поломці числового поля на текстових цінах.

## 7. Ідентифікатор `id` і дедуплікація

- **Джерело `id`:** числовий суфікс у URL оголошення (підтвердити точний патерн на
  етапі GATE №0 / прототипу).
- **Дедуплікація:** `RequestQueue` унікалізує за URL; додатково `uniqueKey` за `id`.
- **Якщо `id` не виділяється:** fallback — `uniqueKey` = повний нормалізований URL,
  у поле `id` пишемо цей самий URL. Лот не втрачаємо.

## 8. Reveal телефону + GATE №0

### GATE №0 — найперший крок реалізації (умова go/no-go)

Перед повною реалізацією перевіряємо, що телефон реально дістається HTTP-запитом.

- **Вибірка:** 10–20 оголошень.
- **Go (підхід A):** телефон отримується окремим HTTP-запитом **без логіну й без
  капчі для ≥80%** вибірки.
- **No-go:** перемикаємось на підхід B (PlaywrightCrawler — реальний клік
  «показати телефон»).
- **Частковий випадок** (потрібен логін, але без капчі): окреме рішення — можливо
  авторизована сесія; не реалізуємо наосліп.

### `phoneStatus` — стани

| Статус | Значення |
|---|---|
| `found` | Телефон успішно отримано |
| `hidden` | Reveal недоступний без логіну / структурно прихований |
| `failed` | Спроба reveal була, але не вдалася (мережа / парсинг / блок) |
| `disabled` | `fetchPhones=false` — reveal не виконувався |

`phoneStatus` важливий саме на ранній стадії — він робить діагностику головного
ризику (reveal) прозорою, а не ховає причину за `phone: null`.

## 9. Обробка помилок і стійкість

- Reveal не вдався → `phone: null` + відповідний `phoneStatus`, лог; **запис не
  втрачаємо**.
- Немає критичного поля (`title`/`url`) → пропускаємо лот із попередженням; решта
  полів — nullable.
- Retries + ротація проксі (Crawlee автоматично); `maxRequestsPerMinute` +
  помірний `maxConcurrency` проти бана.
- Зміна розмітки → усі селектори централізовані в `selectors.js`.
- `listingType` — евристика за ключовими словами/розділом; якщо неоднозначно — `null`.

## 10. Тестування

- **Юніт на збережених HTML-фікстурах:**
  - парсер картки списку (`LIST`);
  - парсер сторінки оголошення (`DETAIL`);
  - нормалізація ціни/валюти/одиниці (вкл. «договірна» → `normalizedPrice: null`);
  - виділення `id` з URL;
  - парсер reveal-відповіді телефону.
- **GATE №0 — прототип reveal** (див. §8): найперший крок, перед рештою реалізації.
- **Окремий тест пагінації:** на фікстурах перевірити, що краулер
  не зациклюється, не плодить дублікати і **зупиняється на останній сторінці**
  (остання сторінка → жодного нового `LIST`-запиту).
- **Димовий інтеграційний тест:** `apify run` на 1–2 стартових URL з малим
  `maxItems`.

## 11. Юридично-етичний запобіжник

Масовий збір телефонів — це збір контактних/персональних даних і може суперечити
ToS Flagma та нормам захисту даних. Для приватного арбітражного використання —
сіра зона. Свідомі запобіжники:

- Помірний темп запитів (не створювати навантаження на сайт).
- Дані використовуються приватно для власної аналітики; **не публікуємо й не
  перепродаємо** зібрані контакти.
- `fetchPhones` можна вимкнути для збору без контактів.

## 12. Поза скоупом

- Арбітражне зіставлення «куплю↔продам» і розрахунок маржі (окремий інструмент).
- Авторизація, обхід капчі.
- Інші платформи (OLX, Prom).
- Розклад і моніторинг (ручний запуск; Apify Schedule — пізніше).

## 13. Критерії успіху

- **GATE №0** дав чітку відповідь go/no-go щодо способу отримання телефону.
- Актор із заданих URL коректно проходить пагінацію, дедуплікує за `id` і збирає
  всі поля.
- Телефон (`phoneStatus: found`) заповнений для більшості лотів у режимі `go`.
- `rawPrice`/`normalizedPrice` коректно обробляють текстові ціни.
- Дані експортуються в CSV/JSON; output schema валідна.
- Задеплоєно на Apify під акаунтом `japan_hat`; успішний тестовий запуск.

## 14. Послідовність реалізації (фази)

1. **GATE №0:** прототип reveal телефону → рішення go/no-go (A чи B).
2. **Скелет актора:** `apify create`, INPUT_SCHEMA, роутер LIST/DETAIL.
3. **Ядро (з тестами):** парсери `LIST`/`DETAIL`, `id`/дедуплікація,
   `rawPrice`/`normalizedPrice`, окремий тест пагінації.
4. **Reveal телефону:** модуль `phone.js` + `phoneStatus`.
5. **Стійкість:** rate limit, проксі, обробка помилок, `sourceStartUrl`.
6. **Output schema** через `apify-generate-output-schema`.
7. **Інтеграційний тест** і **деплой** (`apify push`) під `japan_hat`.
